# Partner organisation administrators and seller accounts

The user explicitly requested implementation: reliable emailed invitations/login, a crowned partner administrator, administrator-managed seller invitations for their organisation, organisation sales comparisons, and sellers limited to their own bookings/results. Implement within each existing supplier (business+supplier); never create a cross-tenant administrator. Use current role=seller plus partner_admin boolean, assigned only by Solvio admin/owner. Existing seller memberships remain ordinary sellers until explicitly promoted in Settings. No automatic privilege migration.

Partner administrators can invite/remove ordinary sellers in their organisation and view organisation bookings and per-seller sales. Ordinary sellers cannot access Team or other sellers' records. Both can create bookings with immutable authenticated creator attribution and existing transactional capacity enforcement. Revocation removes portal membership but preserves history. Admins cannot remove/promote other admins; Solvio staff manage those privileges.

Invitation email controls must be honest: never report sent when test-mode gate blocked delivery. Use one-time email sign-in/setup links with verified auth callbacks and retries for existing accounts, avoiding unrecoverable generated passwords after a failed send. Do not send real emails during tests. Do not alter an existing user's global email/password when another partner invites them. Each invitation/login is bound to the intended organisation and seller identity; an invitation is not a public bearer booking/referral link.

Analytics: explicit date range based on booking creation date, non-cancelled bookings, passenger counts and gross booked value split by currency. Organisation admin sees seller leaderboard (bookings, passengers, sales), ordinary seller sees only self. Unknown/office-created historical rows grouped separately for admins, never wrongly credited. Avoid 1000-row truncation and currency mixing. Crown icon with accessible Admin label, responsive matching current portal style.

Validate local database RLS/direct API isolation, forged creator/organisation/admin flags, admin-only team controls, revoked access, invite blocked/failure/retry/existing login behavior, analytics boundaries, and regression last-seat protection. Rehearse auth callback/browser route where safe; actual inbox delivery needs an approved test recipient and must be explicitly distinguished from mocked delivery.
